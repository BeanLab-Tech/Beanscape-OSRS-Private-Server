## 1. Summary

The infrastructure work (Tailnet-only exposure, RSProx + RuneLite bootstrap pin, systemd, SSH
hardening) is well documented and sensible. The application layer had problems the docs did not
mention:

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 1 | **Critical** | The `dev` realm ships with `ignore_passwords=1` + `dev_mode=1`: **any password logs into any account** (2FA skipped too), and **every new account gets `owner`**. Flipping only `require_registration` (the documented plan) leaves both open. | Fixed by `V9__beanlab_realm_hardening.sql` (deploy + demote existing owners, see §4) |
| 2 | High | GE: partially-filled resting offers were never persisted; after a restart they came back with their full quantity and no proceeds (**item duplication + gold loss**). | Fixed |
| 3 | High | GE: DB writes run on a 4-thread pool with retries, so writes for one offer could land out of order, and they read live mutable objects from a worker thread. | Fixed (snapshots + revision-guarded upsert, one transaction per action) |
| 4 | High | GE: offers are restored asynchronously at boot; a trade placed before restore finished reused offer id 1 and `INSERT OR REPLACE` **overwrote an existing offer row**. Restore errors were swallowed. | Fixed (`GeState.ready` gate, `MAX(id)`, logged errors) |

| 11 | Medium | Repo is an **overlay**, not a full RsMod tree (no Gradle wrapper, engine or settings). `./gradlew build` cannot run here, yet every doc says it can. No CI. | Fixed: `scripts/build-overlay.sh` + `.github/workflows/ci.yml` |

## 2. Architecture

```
GitHub (this repo, overlay only)          Upstream rsmod/rsmod @ fa13b3f6 (rev 233)
  api/db/.../V7..V9 migrations   ──┐        engine/, api/, server/, content/, gradlew
  content/other/grandexchange/   ──┼──copy──► build/upstream/  ──► ./gradlew
  content/other/commands/NameChangeCommands.kt
  docs/, scripts/, .github/      ──┘

VM 123 (/opt/osrs)
  server/rsmod   upstream checkout + overlay, osrs-server.service :43594 (tailnet only)
  discordbot/    Python bot, writes `accounts` rows into the same SQLite file (not versioned)
  tailscale serve :443 -> python :8080 -> jav_config.ws / world_list.ws
Windows client: RSProx launcher -> RuneLite 1.11.19 (bootstrap 4bed6512)
```

How plugins load (verified upstream): `server/shared/build.gradle.kts` depends on **every**
`content/**` project that has a `build.gradle.kts`, and `settings.gradle.kts` auto-includes them.
There is no plugin list and no `data/server.toml`; the docs' "register in `settings.gradle.kts`
and `data/server.toml`" step does not exist.

Persistence: the GE keeps its book in memory (`GeState.book`) and writes through RsMod's
`GameDbManager`. Each request is one transaction on a worker pool; callbacks run on the game
thread. Player inventories are saved separately by the account system, so a crash between a GE
write and the next character save can still desync escrowed coins/items from the book. Closing
that needs GE writes inside the character save transaction (roadmap R6).

## 4. Deploying these fixes (VM 123)

1. Back up: `cp .data/saves/game.db /opt/osrs/backups/game-$(date +%F)-pre-v9.db`
2. Pull this branch into the VM checkout, rebuild, restart `osrs-server`. Flyway applies V8 + V9.
3. **Demote accounts that got `owner` from dev mode** (V9 cannot know who should keep it):
   ```sql
   SELECT id, login_username, modlevel FROM accounts WHERE modlevel IS NOT NULL;
   UPDATE accounts SET modlevel = NULL WHERE login_username NOT IN ('<your admin>');
   ```
   Do this with the server stopped: online players' mod level is written back on save.
4. Test: wrong password is rejected; an unregistered username is rejected; `!register` → login
   works; a non-admin can run `::name` and `::ge`, but not `::master`.
5. Confirm the Discord bot hashes with Argon2 **i** (`Type.I`), as the session report says.

Notes: V9 also turns off `dev_mode`, which only affects new-account `owner` assignment, the
auth bypass and mod teleport speed. To re-enable conveniences later, use `::realm` or SQL — never
`ignore_passwords` on a realm players can reach.
